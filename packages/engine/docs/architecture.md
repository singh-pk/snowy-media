# Architecture

How @snowy-media/engine is built and why. For using it, start with the [README](../README.md).

## One platform

The engine assumes one platform baseline and has exactly one code path for it:

| Feature | Used for |
| --- | --- |
| Cross-origin isolation | `SharedArrayBuffer` between threads, WebAssembly threads |
| WebAssembly SIMD and threads | `@snowy-media/ffmpeg` |
| AudioWorklet | audio output, and the clock everything else follows |
| `OffscreenCanvas` | drawing from a worker, so the main thread never touches a frame |
| WebGPU in a worker | drawing frames: colour conversion and compositing in one pass |
| WebCodecs | hardware video decoding where the browser offers it |
| `importExternalTexture` of a `VideoFrame` | drawing a decoded frame whose planes cannot be read |

`createEngine` checks all of them once, before it starts anything, and rejects with an `UnsupportedPlatformError` whose `feature` names the first one missing. The main thread checks what it can see (`src/platform.ts`); the render worker checks WebGPU, WebCodecs and texture import itself, because only a real worker with a real canvas shows whether they work there. Nothing else in the engine checks for features, so there are no partial modes to test or maintain.

The WebGPU check asks for an adapter, a device and a canvas context and then imports a 2×2 `VideoFrame`, rather than testing that `navigator.gpu` exists: browsers expose `navigator.gpu` and then return no adapter when WebGPU is blocklisted or disabled, and a browser can have WebGPU without being able to import frames in a worker.

## Threads

| Thread | Does | Blocks |
| --- | --- | --- |
| Main | the API, starting and stopping workers | never |
| Media worker | reading the file, demuxing it, decoding and resampling its audio, all with the FFmpeg core | yes, on reads and on a full packet or PCM ring |
| Render worker | WebGPU, WebCodecs | never |
| Video decode worker | decoding the video WebCodecs does not, with the FFmpeg `video` and `video-ext` modules | never; busy while it decodes |
| AudioWorklet | playing the PCM ring, the clock | never |

Each worker is an entry point of its own in `dist/`, loaded by URL, so a thread downloads only its own code. The engine starts both at once, so the FFmpeg core loads while the render worker checks the GPU. The render worker starts the video decode worker the first time a stream needs it, and keeps it.

A file comes as a `FileSystemFileHandle`, never a `File`, so an app can keep it in IndexedDB and open it again on a later visit (the root AGENTS.md, rule 3). `open` gets its `File` on the main thread and posts that to the media worker: `getFile` reads nothing, and the worker's protocol stays a `File`. An open that a later one replaces before it resolves rejects with an `AbortError`, before it changes anything if it is still getting its file, so the state is always that of the last file opened.

The media worker is the one thread allowed to block. FFmpeg reads its input through synchronous callbacks, and the worker answers them with `FileReaderSync` (`src/io.ts`), straight from the `File`: FFmpeg reads only what the demuxer asks for, in reads of up to 4 MiB, never the whole file. Copying the file into WebAssembly memory first would cap it at that memory, and asynchronous reads would need Asyncify or JSPI around every FFmpeg call.

## Packet ring

The media worker demuxes ahead of playback into a ring in a `SharedArrayBuffer` (`src/ring.ts`), from which another thread reads the packets: one producer, one consumer, and no message per packet. Each packet is one record (a large one, several: below), a 32-byte header (stream, flags, pts, dts, duration, size) followed by its bytes, padded to 32 bytes. Each record is copied once into the ring from the WebAssembly heap, and read in place unless it wraps around the end of the ring.

- **Variable-length records that may wrap.** A record of any size up to the capacity fits, with no space lost at the end of the ring and no size class to tune. The 32-byte alignment keeps every header in one piece. A record that wraps is joined in a buffer the consumer reuses.
- **Positions that only grow.** The write and read positions are 32-bit integers that wrap, and the bytes in use are their difference. Each side writes only its own position, so neither takes a lock.
- **The ring being full is the backpressure.** The producer blocks in `Atomics.wait` until the consumer frees room. The consumer never blocks: it waits in `Atomics.waitAsync` on its waiting flag. Each side raises a waiting flag before it checks the other's position, and the other wakes it only when that flag is up, so a wake-up is never lost and a busy ring makes no `notify` calls. The producer takes the consumer's flag as it notifies; a wait that finds it taken returns at once.
- **Watching the producer block.** A consumer can also watch for the producer's thread to block, on this ring or on another one the thread writes, such as the PCM ring. It raises a watch flag before it reads whether the producer waits, and the producer, about to block, takes the flag, adds one to a count of blocks and notifies it; the consumer waits on that count with `Atomics.waitAsync`, and hears each block once.
- **Ending and closing.** A record with stream `END` follows the last packet. A producer that fails raises a flag instead, which takes no room, so it never waits on a full ring that is no longer read; the consumer reads a `FAILED` packet once it has read every record before it, and never waits for packets that will not come. The error itself goes to whoever started the producer, and only there: the consumer stops without a report of its own, so the real error is the one heard. The consumer closes the ring to stop the producer, whose next write returns false; a closed ring holds no packets.
- **Capacity: 8 MiB.** That holds seconds of the highest bitrates a browser plays (4K HEVC at 100 Mbit/s is 12.5 MB a second).
- **A packet of any size passes.** One larger than half the ring, as a 4K FFV1 or ProRes 4444 XQ frame may be, goes as pieces of a quarter of the ring, each marked in its size word, and the last marked as such. The consumer copies each piece into a buffer of its own as it reads it, which frees the piece at once, and returns the packet once the last is in; other records may come between the pieces, but one packet at a time goes in pieces. A producer that offers rather than waits writes the pieces that fit and offers the same packet again for the rest. Smaller packets are one record each, copied out of the ring only when one wraps around its end. Moving packets through the ring takes far less time than decoding them: under 0.5 µs per packet, and over 20 GB/s for large packets, in pieces too (256 MiB in packets of 4 MiB took 8.9 ms, against 17.3 ms whole before they went in pieces). A wake-up takes under 0.1 ms at the 99th percentile (`bench/run.ts`, the `ring` benchmark).

The tests check the ring between two workers, and that the packets of every fixture pass through a ring of 256 KiB, and in pieces through one of 4 KiB, exactly as native `ffprobe` lists them.

## Audio and clock

The media worker decodes the audio itself, with FFmpeg, as it demuxes, and `sny_resample` converts each frame in one call to what the `AudioContext` plays: its sample rate, stereo or the destination's channels, 32-bit float. The samples go into a second ring (`src/pcm.ts`), and the engine's AudioWorklet (`src/audio.worklet.ts`) plays them from there.

- **The PCM ring** is a `SharedArrayBuffer` of interleaved frames with the same growing positions as the packet ring, and its channel count and rate in its header. The producer blocks while it is full. The AudioWorklet may never block, so it never waits: when the ring runs out, it plays silence for the rest of the render quantum. That is an underrun.
- **The AudioWorklet owns the clock.** After each quantum it publishes the media time of the next frame it will play and the context time that frame plays at, and whether it is playing. A reader's media time is that time plus how far the context has moved on since, or exactly that time while it is not playing.
  - **No drift.** The media time is the first frame's timestamp plus the frames played divided by the rate: an exact count, not a sum of durations, and not the context's own time.
  - **An underrun stops the clock** at the last frame played, from the context time that frame plays at; until then the clock runs, since the audio before the underrun is still being heard, so at the end of a file the clock neither jumps by the output latency nor steps back. It resumes from there with the audio. An underrun shorter than the output latency makes `currentTime` step back by up to the gap, since what is heard just after the resume was rendered before it; frames never go back.
  - **Past the audio, silence counts as played,** as far as the video reaches. Once the media worker has written the last of the audio, or at once for a file without audio, it marks the ring finished; it also writes into the header, under a seqlock of its own, how far the video packets it has demuxed reach: the latest end of one, its pts plus its duration. A finished ring that runs out plays silence up to that reach and counts it, so the clock runs on through video that outlasts the audio, or with no audio at all, and stops at the end of the last frame, or at its pts where its packet gives no duration. It runs no further than the packets demuxed, so a slow demuxer stops it as an underrun would, and an audio-only file still stops at its last sample. Without audio the clock starts at the target of the play or seek, or at the first video packet's pts where that is later, as the video of an MPEG-TS file may start hours in.
  - **Context time is render time.** The worklet knows when the context renders a frame, not when it is heard; whoever schedules video against it must add the output latency (`getOutputTimestamp`).
  - **No torn reads.** The three numbers are written between two increments of a sequence word, and a reader that sees it odd or changed reads again (a seqlock), so any thread reads a consistent clock without a lock or a message.
- **Rate and channels are the context's.** The worklet plays the ring as it is; resampling and mixing happen once, in the media worker, where blocking is allowed and FFmpeg already is.
- **One thread fills both rings,** in file order. It queues up to 4 MiB of audio packets ahead of the PCM ring, still compressed, so it demuxes on while the PCM ring is full, and waits only when neither ring has room for what comes next: on a doorbell word in the PCM ring that the worklet rings as it reads and the render worker as it frees room in the packet ring, so one wait misses neither. A consumer of one ring must therefore not wait for the other to fill first: the packet ring and the PCM ring each need room for what the file interleaves between them.
- **Only the core module's codecs play for now.** A stream that needs `audio-ext` is rejected before demuxing starts.

Decoding and resampling are far from the bottleneck: ten minutes of AAC takes about 0.2 s, or 0.5 s resampled from 48 to 44.1 kHz (`bench/run.ts`, the `audio` benchmark).

The tests play every fixture through the worklet into an `OfflineAudioContext`. They check that what plays equals native `ffmpeg -ar -ac` within 10⁻⁶; that while it plays, the clock is at the media time of what plays, without a gap; that it stops after the last frame, which is native FFmpeg's last; and that over ten minutes every click still starts on its whole second, so the clock has not drifted. Underruns, and a producer thread that waits for room, are tested against the ring itself, in Chromium workers (`test/pcm.unit.ts`).

## Video decoder configs

WebCodecs decodes H.264, HEVC, VP8, VP9 and AV1, given a `VideoDecoderConfig` (`src/codec.ts`). The media worker sends each video stream's parameters when it opens a file (FFmpeg's codec name, the container's four-character code, the extradata, the size, any level the container states, the sample aspect ratio, the time base and the display matrix), and the config is made from them and the stream's first packet, a keyframe.

- **The codec string is built as its spec defines it,** from the configuration record (avcC, hvcC, av1C), which also becomes the config's `description`. Where the container has no record (MPEG-TS, raw streams), it comes from the parameter sets in band (the SPS, or AV1's sequence header OBU), in the extradata or in the keyframe, and there is no description: packets then carry their parameter sets themselves.
- **VP9 has no record in WebM,** so its profile and bit depth come from the keyframe's uncompressed header. Its level is the container's, or else the smallest whose picture size fits the stream (VP9 Annex A): browsers decode by the bitstream and the level is only a hint.
- **Non-square pixels set the display aspect** (`displayAspectWidth` and `displayAspectHeight`), so a frame's display size is the size it is shown at before rotation.
- **Frames come out as soon as the stream allows** (`optimizeForLatency`). Without it, Chromium holds more frames than the stream reorders, and in sparse video, a frame every two seconds, a frame was seconds late, until enough packets came to let it out. Decoding is about as fast with it: on an Apple M5, the median of five runs decoding 150 4K frames of H.264, VP9 and AV1 is within 4 % of the time without it in every codec, which is as far as runs differ.
- **The config states the colour the container or codec parameters state** (primaries, transfer, matrix and range, as `colorSpace`), for the frames Chromium converts itself ([Colour](#colour)), and what they leave out as FFmpeg takes it: BT.709 primaries and transfer, the BT.601 matrix, limited range. Chromium otherwise takes what the bitstream states, and VP9's states no transfer: a VP9 HDR stream decoded without it comes out as BT.709 SDR; and fills in the rest its own way, so an untagged stream came out 5 levels off FFmpeg's. The video decode worker gives its frames the same colour, from FFmpeg's decoded frame.
- **The config leaves out rotation and flip.** They are the display matrix's, applied where frames are drawn, the same for every decoder.

The tests check every fixture, but HEVC without a GPU (see [Testing](#testing)). The decoder takes the config and decodes the first packet to frame 0, in the colour `ffprobe` says the file states. The codec string equals the one native FFmpeg writes, where it writes one (H.264 and AV1). The same holds for each stream converted to how a container without a record carries it: Annex B, its parameter sets in band. Unit tests (`test/codec.unit.ts`) cover the spec's HEVC example, VP9 profile 2, and AV1 sequence headers with timing and decoder model information, a high tier, and 10- and 12-bit depths.

## Video output

The render worker decodes a video stream's packets from the packet ring and shows them through the compositor (`src/video.ts`). The media worker names each stream's decoder by its codec: WebCodecs for H.264, HEVC, VP8, VP9 and AV1, where the browser decodes in hardware, and otherwise whichever FFmpeg module holds the codec's decoder, `video` (MPEG-2, MPEG-4 Part 2, ProRes, DNxHD, FFV1 and the other codecs real files use) or `video-ext` (the rest). With WebCodecs, the packet's data goes straight from the ring into an `EncodedVideoChunk`, which copies it, so the ring frees it at once.

- **FFmpeg decodes in a worker of its own** (`src/video.worker.ts`), because it decodes synchronously, in software, which in the render worker would hold up its animation frames for as long as each frame takes. The render worker stands it in for a `VideoDecoder` (`src/wasm-video.ts`): it reads only a packet's header from the packet ring and sends the worker where its bytes are; the worker copies them from there straight into the module's memory and says so, and only then does the render worker free the record. A piece of a larger packet goes the same way, and the worker puts the pieces together. The worker answers each packet once decoded, as a `dequeue` event, and sends each frame back in a ring of its own, so the rest of the video output is the same for both. The worker loads a module the first time a stream needs it (`video-ext` only for its rarer codecs) and keeps it, so a seek or another file does not load it again, and decodes with up to 8 threads. Each frame is converted, only where FFmpeg's pixel format is not one a `VideoFrame` takes (`sny_to_video_format`); otherwise it is referenced where the decoder left it, so its buffers are not reused while it is held; its display size comes from the sample aspect ratio. A packet the decoder rejects is skipped, as a hardware decoder would conceal it.
- **Packets and frames go through rings, not messages.** The render worker makes the two rings (`src/ring.ts`) when it starts the worker and sends them once; after that only a module's memory comes by message, once it loads, and each decoder's packet ring as it opens. Each record's stream holds the decoder's id and what the record is: to the worker, a decoder opening, a packet's place in the packet ring, a flush, a close, or a frame going back; from it, a frame, a packet ring record taken, a packet decoded, a flush done, or a failure. The ring to the worker holds 1 MiB of small records: one packet's place at a time, as the render worker waits for each to be taken before it reads the next, and the frames shown meanwhile going back; the ring back holds 64 KiB. Copying a packet straight out of the packet ring, rather than through the ring to the worker, takes the render worker's share of a 4K ProRes HQ stream at 911 Mbit/s from 3.2 ms a second to 0.34 on an Apple M5, with no frame late and about the same CPU in all (4.14 cores against 4.10), as the copy moves to the worker; and on a budget laptop, from about 10 ms a second to 0.35, where that stream stays decode-bound at 3.7 s played of 8. Waiting for each place to be taken costs the decoder nothing it can measure: it decodes that stream at 1106 frames a second, against 1040 to 1077 before. Without a message for each packet and frame, a packet is not copied into a buffer of its own first, and nothing is cloned for each. On an Apple M5, the decoder keeps up a third faster when nothing holds it back: 4K ProRes decodes at 1040 frames a second instead of 755, and 4K DNxHR at 2255 instead of 1690 to 1930; playback, which the clock paces, uses about the same CPU as before (2.27 cores instead of 2.30 for that ProRes).
- **FFmpeg's frames are never copied on the CPU.** The module's memory is shared, so the render worker gets it once and each frame as where its planes start and their strides, and `writeTexture` uploads them from there straight to the GPU. Packing a frame, making a `VideoFrame` of it and `copyTo` took three copies of it before that upload. Once uploaded or dropped, the frame goes back to the worker, which frees it between packets, so its buffers return to the decoder. The frames held are the frame queue's, bounded by bytes as before, but in the module's memory, which then stays that large. A 4K 10-bit 4:2:2 ProRes stream, the heaviest of these, plays on 2.28 CPU cores instead of 2.41 on an Apple M5; MPEG-2, with frames under half the size, uses the same as before.

- **The frame queue** (`src/frames.ts`) keeps decoded frames in presentation order, whatever order they arrive in, and is bounded by the bytes they hold, 64 MiB: two or three 4K 10-bit frames, hundreds of small ones. A frame on the GPU, without a pixel format, counts as RGBA.
- **Frames come out in any order.** Video counts as decoded up to the latest frame out, but no further than just before the earliest packet whose frame has not come out, or the last packet given to the decoder (a packet still to come is due after its dts). So preroll and the tests wait for every frame before a time, whatever order the decoder emits them in. A packet that makes no frame is not waited for (`src/decoding.ts`): a VP8 alt-ref frame, which WebM stores as a packet of its own, by its `show_frame` bit; and any other once a frame fed more than 32 packets after it has come out. How long a decoder holds frames delays them all alike, so that bound is on how far the stream reorders: twice the 16 frames of an H.264 or HEVC decoded picture buffer. A stream that reorders further, or stores a field a packet, may count a frame decoded before it comes, which then shows late or is dropped, but never holds play. A frame that comes out after a later one has gone up is dropped, so video never goes back.
- **Closing** stops decoding at once, wherever it waits, and closes every frame; it is not a failure. The main thread closes the packet ring as it stops a play, before the render worker hears of it, unless a file opens (below); decoding then ends where it finds the ring closed, as a wait for packets would end at once, again and again, and keep the stop message from coming in.
- **Decoding waits** while the queue is full, every frame is decoded to more than a second past the media time shown (or the first frame, before one is), counting a frame the decoder holds back as not decoded, or the decoder holds 8 packets it has not decoded, and goes on when a frame is shown, the media time comes within a second, or the decoder takes a packet (its `dequeue` event); it looks again each time. Neither memory nor the decoder's backlog grows. The packets come far further ahead than that second (below), and decoding all of them would hold hundreds of frames, far past the byte budget and a hardware decoder's pool of frames. A hardware decoder's pool of frames may run out before the byte budget does; in playback the frames come back as they are shown, so decoding goes on. From a seek, the frames before its target are closed as they arrive, all but the latest, or the pool would stall it.
- **The last frames a stream reorders,** as many as it reorders (two, for x264's B-frames), come out only when the decoder is flushed, at the end of the stream. The media worker gets there as far ahead of the clock as the packet ring (8 MiB), the audio packets it queues and the PCM ring hold, so in video that ends before the audio, or sparse video, those frames come out before they are due unless the rings fill first.
- **Presenting** shows the latest frame due at the media time and closes the ones before it, which were never shown in time; the frame on screen is closed when the next one replaces it. Timestamps are the packets' pts in microseconds, rounded, or their dts where they have no pts, which is right for a stream without B-frames; a packet with neither is an error. Before the stream's first frame is due, as at the start of a file whose video starts after its audio, the first frame stands for the time before it (the stream's start time says when that is). From a seek, nothing goes up until every frame due by its target is decoded, or the stream has ended, so the frames before the target do not flash by.
- **HEVC pictures that lead a CRA** (RASL), which follow it in decoding order but refer to pictures before it, are left out when decoding starts at that CRA, as after a seek into an open-GOP stream such as x265 makes by default; H.265 has a decoder starting there do the same.
- **The compositor** (`src/compositor.ts`) uploads a frame into textures of its own, a picture, and closes the frame. It uploads only the frames that go up: the latest frame due, once every frame up to it is decoded (as each frame is decoded, when a scrub moves on, and on each animation frame), and then the next two decoded in playback, so they are up before they are due even as the clock jumps a frame, as when audio starts. A scrub holds the time at its target and moves on far past the frames after it, so there only the next one goes up ahead, not to hold up the frame due at the next target. Copying a 4K frame off the GPU takes milliseconds, and a scrub decodes many frames it never shows: uploading every frame put the frame on screen in a 4K scrub 181 ms behind the drag at p90 (Apple M5). It is now 35 to 56 ms behind from run to run, against 35 ms with Chromium's zero-copy import: the upload, about 7 ms for a 4K frame, sometimes misses an animation frame. A frame due but not yet uploaded goes up on a later animation frame. Uploads run one at a time, in order. A picture's textures come from a pool kept for the frame's format and size, and go back to it when the picture is closed; a frame of another format or size empties the pool. The compositor draws a picture with one triangle over the canvas. Its uniform maps the canvas to the picture's texture through the inverse of FFmpeg's display matrix, so rotation and flip cost nothing, fitted and centred with black around it. A frame allocates no textures, buffers or bind groups, and reuses the descriptors of its upload; what is left is the `EncodedVideoChunk` each packet needs, the promises of its upload, and the command encoder and pass of each draw. Where Chromium converts a frame ([Colour](#colour)), an external texture lasts one task, so that frame needs a bind group and a pass of its own.

The tests (`test/render.test.ts`) decode every fixture from the ring into a canvas they read back. Each frame goes up at its own timestamp with its own number, stays up halfway to the next, and a jump shows the frame due and skips the rest. The first frame, drawn at the size it is shown at, has the layout of native FFmpeg's, rotated and mirrored fixtures included: their brightness grids correlate above 0.9, where a mirrored one comes to about 0.76 and one turned the wrong way below 0. Its levels are FFmpeg's, less than 2 apart on average (under 1 for every fixture but the HDR one, which Chromium converts); unit tests (`test/frames.unit.ts`) check the conversion against pixels FFmpeg converted.

### Colour

The compositor converts Y′CbCr to R′G′B′ itself, in its shader, rather than Chromium, which converts the same frame differently by the decoder it came from: a hardware decoder's frames and a software decoder's do not match, and an untagged stream gets BT.709 from one and BT.601 from the other. It converts as FFmpeg does, so every decoder's frames look as native FFmpeg shows them:

- **The colour is the stream's** (`VideoParams.colorSpace`), as the container or codec parameters state it, not the frame's: Chromium fills in what a stream leaves out its own way. A stream that states no matrix is BT.601 and one that states no range limited, as FFmpeg takes them.
- **A WebCodecs frame is drawn straight from the GPU where Chromium converts it as FFmpeg does.** Copying a frame's planes back off the GPU (`copyTo`) costs CPU, so the compositor imports the frame as an external texture instead and draws it once into an RGB picture of its size. Whether Chromium's conversion matches differs by OS, GPU and decoder, and only a frame shows it: on macOS, Chromium gives some hardware decoders' BT.709 frames (HEVC's, on an Apple M5) Apple's BT.709 transfer, a pure 1.961 gamma, and still reports them as plain BT.709. So the compositor measures each stream's frames (`src/measure.ts`): the first frame with enough midtones and enough colour is drawn both ways, imported and from its planes, at the centres of the pixels nearest a grid of 128 × 72 points, where the two sample alike, and the channels between 10 % and 90 % compared (a sharp frame, such as colour bars, has midtones only along its edges); a near-grey frame shows a transfer but not a matrix, so it decides nothing. A stream with no such frame in its first 60 measured, or whose measurement fails, has its planes read. Within 1.5 levels of 255 at the median and 6 at the 95th percentile, its frames are imported from then on; within them once Apple's gamma is undone, they are imported and the shader undoes it. Failing both, the same two are tried through each matrix and range Chromium may have taken instead of the stream's, BT.601 or BT.709 in limited or full range: the shader takes Chromium's R′G′B′ back through that matrix to the planes and on through the stream's, both affine, so the planes' own R′G′B′ comes back wherever Chromium did not clip. Apple's gamma is undone mirrored about 0, as Chromium encodes a value below 0, since the matrix then mixes the channels. Where Chromium clips, as into an 8-bit texture, a saturated colour would not come back, so a matrix is undone only from a frame that shows Chromium's conversion both below 0 and above 1, by more than two levels at 10 channels or more each. A frame whose colours all fit inside, or that Chromium clips, shows nothing either way and decides nothing, so the next frame is measured: a later, more saturated one may show the matrix. An untagged 4K H.264 stream whose first two seconds are desaturated, on an Apple M5, is decided at its 58th measured frame, two seconds in, and plays its first 8 seconds on 0.26 cores instead of the 0.35 it takes with its planes read. The 60 frames are about two seconds at 30 frames a second, and one at 60. A stream whose unclipped frame matches none of these keeps its planes read. On an Apple M5, Chromium converts the untagged 4K H.264 of the scrub benchmark, which FFmpeg takes for BT.601, as BT.709 with Apple's gamma, values from −0.33 to 1.17; undone, it draws within 0 levels at the median and 1 at the 95th percentile of its planes, and plays on 0.19 to 0.20 cores instead of 0.29 to 0.31, and on the low-end profile on 0.12 to 0.19 instead of 0.45 to 0.52, every frame on time. A stream whose primaries or transfer Chromium would convert, such as BT.2020 or PQ, is never imported: comparing levels shows a transfer reliably, but not a gamut. This is the one check outside the platform check ([One platform](#one-platform)): it chooses no feature, only which of two conversions of the same frame matches FFmpeg's. On an Apple M5, H.264, VP9 and AV1 frames import within 0.23 levels at the median and 0.47 at the 95th percentile, and hardware HEVC frames with Apple's gamma undone within 0.005. The tests draw every WebCodecs fixture both ways and check that the two drawings match where the route imports. Hardware-decoded H.264 and HEVC streams play on about a third less CPU, every frame shown: 4K60 H.264 on 0.29 to 0.34 cores instead of 0.44 to 0.46, and on the low-end profile ([Low end](#low-end)) 0.33 to 0.36 instead of 0.52 to 0.91; 4K HEVC on 0.23 to 0.24 instead of 0.30. VP9 and AV1 frames at 4K, which Chromium gives without a pixel format, were imported already.
- **Planes are read as integers.** Otherwise `copyTo` copies a frame's planes into a buffer the compositor keeps, and each goes into an unsigned integer texture of its size, 8 or 16 bits a sample; the shader filters them bilinearly itself, because a 16-bit texture can neither be filtered nor even made without an optional feature. One 4×4 matrix (`yuvMatrix`) takes the plane values, at any bit depth and either range, to R′G′B′; planar RGB (G, B, R) only scales by the range, full unless the stream states it limited. An RGB frame goes into a texture as it is.
- **A frame whose planes cannot be read,** without a pixel format, as Chromium gives a 10-bit frame from the GPU decoder, Chromium converts: the compositor imports it as an external texture and draws it once into a 10-bit RGB picture of its size.
- **Not yet:** the transfer and primaries are left as they are, so HDR shows as its signal, as FFmpeg shows it without a tone-mapping filter, and BT.2020 primaries are not converted to the canvas's. Chromium tone-mapped a software decoder's HDR frames before; it still does a GPU decoder's.

## Playback

`engine.play()` plays the open file's first video and first audio track through all three threads, and `pause()` holds it.

- **The main thread** makes one `AudioContext` on the first play and keeps it, starts the worklet on a PCM ring of a power of two frames, a second and more at the context's rate, in stereo, asks the render worker to play the video from a packet ring, and asks the media worker to demux into both. The media worker fills both rings in file order, so the PCM ring and the audio packets it queues are what let it demux video ahead of the audio.
- **What is heard now** is the one thing every thread needs and only the main thread can read: `AudioContext.getOutputTimestamp()` says which context time is being heard at which moment. The main thread publishes it into the PCM ring's header on every animation frame, with whether the context runs, under a seqlock. Until output starts the timestamp is zero, which is published as not running, so nothing is shown ahead of what is heard. Any thread then gets the media time heard at any moment, on the clock of `performance.timeOrigin + performance.now()` that all threads share: the context time heard then, carried forward from the timestamp while the context runs, through the worklet's clock. The output latency is in it, as the browser reports it.
- **Starting** suspends the context, which a user gesture or the last file may have left running, and waits, before it resumes, for the render worker to decode a quarter of a second of video (or, once the media worker is blocked, as much as the frame queue holds) and for a quarter of a second of audio in the PCM ring (or the whole file, if shorter, or nothing without audio), so a slow start delays both together instead of letting audio run ahead or underrun. While the context waits, nothing drains the PCM ring, so the wait also ends when the render worker says video is stuck: the media worker is blocked, on a full PCM ring or a full packet ring, and video gets no further, as it waits for packets with nothing to decode (sparse video) or its frame queue is full or a second ahead (a short audio track). Every step is an event, with no timer and no polling. The media worker says once that the audio is buffered: a quarter of a second written, a full PCM ring, or all of it, or at once without audio. The render worker works out how far it has decoded on each event that may change it: a frame decoded, the decoder taking a packet, a wait for packets or for the media time begun, the end decoded, and the media worker blocking, which it watches for through the packet ring. It reports each change until a frame is on screen by the running clock with none due by it still going up; a decoder slower than the clock still lets it get there, with the latest frame it has. A hidden page waits to be shown before it starts audio, as its animation frames, and so video, wait too. A decoder slow to start delays play until it decodes. One that stops taking packets with frames out, as a hardware decoder whose pool has run out would, gives no event, and would hold play; no test has shown it. Chromium may hold `resume` until a user gesture; `play` waits for it and for a stop together, so a pause, an open or `close` meanwhile settles `play` all the same. A pause ends it as well; `play` resolves once audio is heard, by an output timestamp that has settled, and the frame due by it is on screen. The first timestamps after output starts are estimates, which Chromium corrects by up to 35 ms, so the clock runs only once two in a row agree with the one before within 2 ms, or after ten, for timers too coarse to agree; after that it keeps running until the context stops.
- **The render worker** shows, on each of its own animation frames, the frame due when that animation frame reaches the screen: its start plus the refresh interval, the shortest of its last eight gaps, so one late animation frame does not move the next one's target. `engine.currentTime` is the same media time, read on the main thread.
- **Pausing** suspends the context: the worklet stops, the timestamp stops running, and the clock and the frame stop with it. The stopped timestamp is published as the context suspends, not on the next animation frame, so `currentTime` holds once `pause` resolves, in a hidden page too. It holds the time heard as the context suspends: the last timestamp carried forward to then, no further than the worklet rendered, published as that media time until a timestamp after `play` passes it, so it never goes back. The last timestamp itself is up to an audio callback older, and the frame on screen went up by it carried forward. A clock stopped at it went back by up to 20 ms on an M5, and left the frame on screen two frames ahead on 2 pauses in 150. The frame on screen stays, and may be a frame ahead of the clock: it went up for a refresh later. Frames never go back until seeking does.
- **Opening a file, or a failure,** stops what plays: both rings are closed, which frees the media worker, the worklet ends, and the render worker closes its frames. An open also clears the canvas to black, so nothing of the file before stays up; the render worker hears of it first, and stops before the ring closes. A `play` still starting when an open comes rejects with an `AbortError` and sends nothing, as the media worker may already hold the new file; a `pause` that comes while `play` starts wins. Each play has an id, so a failure reported late for one that has stopped is ignored. A failure in either worker makes the next `play` or `pause` reject with it, until the next open, and `currentTime` reads 0 meanwhile; nothing else signals it yet.
- **Seeking** stops what plays and starts it again from the target, with fresh rings: the PCM ring's start is the target, so the clock reads it before audio is heard. The media worker moves the demuxer to the keyframe due at or before the target on the first stream, video if there is one (or the first keyframe, if the target is before it), converting the target to the stream's time base exactly, rounded down. MP4's demuxer, among others, seeks by dts, so it can land on a keyframe due after the target, as an open GOP's CRA is, with its leading pictures due before it; the media worker reads that keyframe's pts, and seeks again from just before its dts until the keyframe is due by the target. It drops the audio before the target, to the sample, rounded down, so the clock starts at most a sample before the target, never after it, and the render worker shows no frame due before the target; where the audio after a seek starts later, as Opus drops its first frames after one, it writes silence from the target up to it, so the clock reads the target to the sample. The render worker decodes from the keyframe, closes the frames before the target as they arrive but the latest, and prerolls from the target. Paused, `seek` resolves once the GPU has drawn the frame due at the target, not once it is sent to the GPU: a GPU that compiles a draw the first time it runs, as SwiftShader does, took a third of a second to show the first frame of a page, under Docker on an Apple M5. Playing, it resolves as `play` does, and a pause before it starts makes it a paused seek. A seek during a `play` that is starting restarts it from the new target, and a seek that a later one replaces resolves.
- **Scrubbing** (`fastSeek`) is seeking called on every pointer move, faster than a seek can finish. One scrub is under way at a time; a call meanwhile only replaces where it goes next, so the screen follows as fast as the engine decodes, not as often as it is called, and no call starts work that a later one would throw away. Forward of where it is, with no keyframe on the way up to the target, it does not start again: the render worker moves the play's target on, drops the frames before it, and shows each frame it decodes on the way, as decoding goes on from where it is. A keyframe on the way, or a target behind, starts again from the keyframe at or before the target, as a seek does; so does the first scrub after playing, as the frame then on screen may be up to two frames past the clock. The keyframes are the demuxer's index, read when the file opens: an MP4's samples, or a Matroska or WebM file's cues. It is known only as far as its last entry (a fragmented MP4 holds only the fragments read so far), and a target past that, or a file without one, starts again. A play moved on this way never plays its audio, as `play` after a scrub starts again from where the scrub is: its PCM ring is closed at the first move, so the media worker drops the audio and demuxes on for the video however far the scrub goes. `currentTime` reads the scrub's target meanwhile. Each call resolves once the GPU has drawn the frame due at the last target.
- **A hidden page** has no animation frames, so a `play`, or a paused `seek` or `fastSeek`, there resolves, and video runs, once it is shown.
- **Not yet:** a choice of track, and audio far into the file: if more video comes before the first audio than the frame queue and the packet ring hold, play starts with the media worker blocked short of the audio, and the clock never moves. Video that goes on past the end of the audio by more than the packet ring holds (8 MiB, about 13 s at 5 Mbit/s) plays only to the end of the audio: the media worker marks the audio finished only at the end of the file, which it reaches only as the clock moves on. A video stream that neither WebCodecs nor FFmpeg decodes fails when it starts. Packet side data does not reach the decoders, so paletted video whose packets carry the palette, such as 8-bit QuickTime RLE, decodes with the wrong colours.

The tests (`test/play.test.ts`) play `sync-10min.mp4` in real time, through the public API alone, reading the frame number off the canvas on every animation frame of the page: the frame on screen is the one due at `engine.currentTime` within 20 ms, from the first animation frame, and a pause holds both. On CI's runners, a virtual machine's GPU on macOS or software on Windows and Linux, Chromium does not draw in real time: on macOS, its page gets 30 animation frames a second, and video falls behind by up to three quarters of a second (p99 82 ms). There the test checks that the clock runs in real time (losing at most a second) and that a pause holds, bounds lateness by a second, earliness and the 99th percentile by 0.15 s, and logs its percentiles; the 20 ms bound holds on real hardware, and in the ten-minute run. CI plays 20 seconds; `SNOWY_SYNC_SECONDS=600` plays all ten minutes. A second test plays sparse video (a frame every two seconds), a tenth of a second of audio under three seconds of video, video that starts half a second after its audio, three seconds of video without audio from half a second in, and the long file, each for two seconds, pauses, and plays on for two more: play starts where video or audio gets no further, the clock starts and resumes where it was and runs in real time up to the later end of the audio and the video, and the frame due is on screen throughout and as it pauses, within the same bounds on each frame. The first read is left out: it now and then shows a frame from five or more frames before, with the due frame on the next read under a millisecond later, which is the quarter second of video play prerolls, not a late frame.

The seek tests (`test/seek.test.ts`) seek each fixture with video, with audio or without (where the clock reads no earlier than the first frame), paused, to its start, its end, a frame's own time, halfway between two frames, its first frame, and at random: the frame on screen 100 ms later is the one due at the target by native FFmpeg's timestamps, and the clock reads the target within 0.1 ms. That last read is the one checked, as a read may show the canvas as it was a few frames before, and the frame before a seek can have any number. CI seeks ten times a file; `SNOWY_SEEKS=50` seeks fifty. A second test seeks the long file five minutes in while it plays: it plays on from there in real time, with the frame due on screen. A third scrubs `h264-aac.mp4` from its start to its end and back, a `fastSeek` on every animation frame: each way shows more than twice as many frames as the keyframes it passes, none past the scrub, the frame where it is let go is exact, and it plays on from there; paused again, a scrub back behind the clock lands exactly too.

## Compositions

`engine.compose(composition)` plays a composition: a length in microseconds, a `plan(from, to)` of what plays over a range of it, and `source(asset)`, the `FileSystemFileHandle` of an asset. The plan's shape is the engine's own (`src/composition.ts`), and the render plan of `@snowy-media/timeline` fits it, so the engine depends on no other Snowy package. It has segments of video and audio layers and their transitions. Times on the composition are microseconds, and each layer reads its file from an in point in its stream's time base, at a speed, from its start to its end.

- **One clip of one file.** The engine plays a plan's one clip: a video layer, an audio layer or both, of one file, in step (the same start and end, and in points less than a tick of the coarser time base apart, since a timeline gives a picture and its sound as two clips, each in its own stream's time base), within the composition's length, at a speed of 1, with no effect, transition, opacity, blend, transform, gain, pan or fade. A plan that asks for more fails with a NotSupportedError that names it. The plan is read once, over the whole composition, when it opens.
- **The workers keep the file's time.** A clip plays from `in` to `out` of its file, placed `offset` later on the composition. The main thread adds the offset to the clock for `currentTime` and takes it off a seek's target, so the media worker, the render worker and the worklet see only the file's time. The player is the same path with no clip: `open` plays the whole file, at its own times.
- **Gaps are black and silent, and the clock runs through them.** A play starts its clock at its target, which may be in the gap before the clip. The media worker reads from the clip's in point at the earliest, and the audio decoder writes silence from the clock's start up to the clip's first sample, as it does after a seek. The render worker draws black while the clock is outside the clip's window. In the gap before the clip, it uploads the clip's first frame ahead, so the frame is up when it is due. Within the clip, a frame stands for the time before it, as in a file whose video starts late, so a clip never flashes black at its start.
- **The clip ends at its out point.** The media worker writes no packet of a stream from the first one whose dts reaches the out point, because every later packet in that stream is due later still. Once every stream has got there, the media worker ends the packet ring as at the end of the file. The audio decoder writes no frame past the out point. The clock's reach (see Audio and clock) goes no further than the out point while the clip plays, then on to the composition's end, so the clock runs through the gap after the clip and stops at the end. A play that starts past the out point reads nothing: the main thread finishes the PCM ring and sets its reach to the end itself.
- **An edit** is `engine.changed()`. The engine reads the length and the plan again, and with the same length, a clip with the same file, streams, in and out points and offset plays on. Anything else opens again, and the composition goes on from the time it was at, playing if it was, unless the app seeks or pauses while it opens; then that has the last word.
- **Not yet:** cuts between clips, more than one layer, transitions, effects, speeds, gain, pan and fades, generators, and compound clips. Each fails as a plan the engine does not play. A clip whose audio ends before its out point has the media worker read, and pass over, the rest of the file, since it stops at a clip's end only once each stream it reads has got there.

The composition tests (`test/compose.test.ts`) compose a clip of `h264-aac.mp4`, read from 0.5 s and placed from 1 s to 2.5 s of 3.5 s, through the public API alone. Played, the canvas reads black before and after the clip, and shows the frame due at the composition's time less the offset in between, by native FFmpeg's timestamps, within the bounds the play tests use. The clock stops at the end. Paused, a seek into each gap and into the clip lands on black or on that frame exactly, with the clock at the target. An edit that moves the clip leaves the time where it was, now in the gap, and shows black. A plan with two video layers is refused. The audio tests play a clip of the same file through the worklet: of the file's clicks on its whole seconds, only the one inside the clip plays, at its time in the file, and the clock runs from the composition's start, through the silence, to its end.

## Bundling

`dist/` keeps `@snowy-media/ffmpeg` as an import, so the app's bundler resolves it and the WebAssembly files it loads by URL, and an app can update it on its own. The tests have no bundler: `scripts/build.ts` builds them into `test/dist/` with the imports pointing at `/ffmpeg/`, where the test server serves the ffmpeg package.

## Testing

The tests run the engine in Chromium through Playwright, with a GPU, because WebGPU on a software renderer alone would leave the code real users run untested. CI's Windows and Linux runners have no GPU, so there Chromium runs WebGPU in software, chosen by `SNOWY_GPU` (`test/support/browsers.ts`): on Linux SwiftShader, Chromium's software Vulkan; on Windows WARP, Windows' own software Direct3D 11, the software adapter Chromium's WebGPU takes there. Without a GPU, WebCodecs decodes in software, with Chromium's own decoders, so only macOS covers hardware decoding and the frames that only a GPU decoder gives (a 10-bit frame imported as an external texture, [Colour](#colour)):

| Runner | Chromium |
| --- | --- |
| macOS (CI: `macos-26`) | the GPU, with `--enable-gpu` |
| Windows (CI: `windows-latest`) | WARP, with `SNOWY_GPU=warp` |
| Linux (CI: `ubuntu-latest`) | SwiftShader, with `SNOWY_GPU=swiftshader` |

On Linux, SwiftShader needs ANGLE and Chromium's compositor on it too (`--use-angle=swiftshader`, `--enable-features=Vulkan`, `--use-vulkan=swiftshader`): without them, a canvas cannot be read back and a frame cannot be imported as an external texture. Without a GPU, Chromium decodes no HEVC, which it decodes only in hardware, so there the tests leave out the HEVC fixtures, which macOS tests on its GPU. So CI runs the engine tests on all three; the benchmarks also run on each, for reading only. The checks that a browser can be made to fail have a test where they do: a page without cross-origin isolation, and WebGPU switched off.

### Low end

`bun run test:low-end` and `bun run bench:low-end` run the tests and benchmarks as on a budget laptop (`SNOWY_PROFILE=low-end`, `test/support/browsers.ts`). Each page's renderer, which runs the page and its workers and so all of the engine's own work, decoding in software included, is put on the efficiency cores at background priority, for CPU and I/O (`taskpolicy -b`). The browser and GPU processes, which composite and drive the hardware decoders, keep their speed, as a slow laptop's GPU and media engine still play hardware-decoded video smoothly; slowing them too dropped the animation frames to about 12 a second, which no laptop does.

On an Apple M5 that leaves six efficiency cores for the engine, about the work of one and a half of its performance cores, measured with eight workers spinning: each took 8.5 s instead of 1.6 s. That is roughly a four-core budget laptop. It needs a Mac with efficiency cores, and fails elsewhere rather than run unconfined. CI's `macos-26` runners are virtual machines without them, and are slow machines themselves: three cores.

Work that moves decoding or conversion onto the CPU runs both before it merges. The tests have to pass as they are, and the benchmarks' numbers go in the pull request, `play cpu cores` included. That counts every browser process, the benchmark's read-back of the canvas on each animation frame too, so it compares runs on one machine and profile only: a second on an efficiency core is less work than one on a performance core. Without such a Mac, say so in the pull request, and a maintainer runs them.

## Fixtures

`scripts/gen-fixtures.ts` makes the test videos with native FFmpeg 9.0.2, the version `@snowy-media/ffmpeg` builds, and takes every expectation (format, codecs, sizes, colour, timestamps, keyframes, duration) from native `ffprobe`. It covers H.264, HEVC, VP9 and AV1 in MP4, Matroska and WebM, with AAC or Opus; for the FFmpeg modules, MPEG-2 and MPEG-4 Part 2 with B-frames, 10-bit 4:2:2 ProRes, 10-bit 4:4:4 FFV1, and QuickTime RLE in RGB, from `video-ext`; a 10-bit VP9 HDR10 file (BT.2020, PQ) whose colour only its container states; plus a variable frame rate file, a file with a frame every two seconds, one with a tenth of a second of audio under three seconds of video, one whose video starts half a second after its audio, a two-pass VP8 file with alt-ref frames, a ten-minute file for drift, a 4K file with one keyframe in ten seconds for the scrub benchmark (its frame numbers twelve times the size, so they read the same at 320 × 180), and files whose display matrix turns them a quarter turn, and also mirrors them. For each, it records the first frame as FFmpeg shows it, as a grid of mean brightness.

Each frame shows its own number in binary, as a row of 16-pixel squares in the top-left corner ([`test/support/frame-id.ts`](../test/support/frame-id.ts)), and the audio clicks at every whole second. A test reads which frame is on screen from the canvas alone, after any decoder and colour conversion, and the clicks mark known instants in the audio. Squares this size survive every lossy codec in the set. The generator decodes every fixture natively and stops if a single frame number or click is more than a millisecond off, so a broken fixture never reaches a test. The output is reproducible (`-fflags +bitexact`, a fixed keyframe interval).
